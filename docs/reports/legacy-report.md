# Legacy and Backwards-Compatibility Audit

Three audits, twelve lenses, seventeen waves of cleanup — all landed as of 2026-08-07. The first audit (2026-08-06) swept the tree for obvious dead code (Waves 1-5). The second (2026-08-07) reorganized by *kind* of legacy rather than region of tree — twelve independent lenses — and found roughly 100 items the first never saw (Waves 6-12). The third (2026-08-07) re-ran the lenses with per-finding adversarial verification: 96 findings, 93 confirmed, 2 refuted, 1 routed to a decision, collapsing after cross-lens dedup to 64 mechanical removals (Waves 13-17, net −742 lines). Everything mechanical is done. The drift mechanism previously flagged as unguarded (end of §2) turned out to be already closed by commit 2862a6e6. §3 was the last actionable section — eighteen independent waves, one per decision, each implementable in isolation; all eighteen landed 2026-08-07, and it is now a record rather than a plan. **Nothing in this document is open.** The one remaining action belongs to the maintainer, not to a wave: `git add input/examples` to stage the three files decision wave 15 made shippable.

The durable finding was never the dead code — it was **drift**: hand-maintained lists that silently stopped mirroring their registries, docs prescribing env vars the CLI no longer reads, schemas documenting capabilities never implemented. Dead code is harmless until someone reads it; drift actively misleads. Every user-visible defect these audits found was drift, and §2 lists the guards that now make each class of it self-detecting.

Three lessons that outlived their waves:

- A `[verified]` mark records that a finding's *observation* was confirmed, never that its *prescription* was — four Wave 10 items would have made things worse applied as written (a new dead alias, a regressed warning suppression, a fleet of non-resumable manifests). Decision wave 1 hit a milder form of the same edge: four of its eight prescribed retargets would have restated something the file already contained verbatim, so they became deletions plus one strictly stronger rejection pin.
- Never bump an artifact `schemaVersion` without shipping the upgrader in the same change: four hard `schemaVersion !== 2` rejects exist with no migration code anywhere, so a bump alone makes every manifest on disk non-resumable.
- Dead *symbols* and dead *reachability behind live symbols* are different classes: optional parameters no caller passes survive symbol-level sweeps and need per-option call-site enumeration to find (all of Wave 14 was this class, which is why it survived two audits).

## 2. Verification bar and guards

Per change: `bun run check`, then the no-cost smoke set (`cli-help-contracts`, `cli-usage-errors`, `option-resolution-contracts/`). `bun test test/test-cases/validation/` is green (1266 tests across 186 files); treat any failure as real — the old standing allowance for pre-existing failures was withdrawn 2026-08-07. One known exception, unrelated to any wave: `process-lock-contracts.test.ts`'s "process lock serializes separate processes" is timing-sensitive and flaked twice in six full-suite runs on 2026-08-07, passing on immediate re-run both times. Never run paid-provider commands to verify anything in this document; paid e2e suites cited as pins are read-only citations, not instructions to execute.

Shipped guards, each replacing a hand-maintained mirror with a derived source or a two-direction pin:

- `registry-derived-config-keys.test.ts` — every step-2 registry `configPath` parses under the strict config schema.
- `getHostedProviderEnvKeysForConfigPrefix` — setup's credential catalogs are derived, not typed.
- `help-flag-groups.test.ts` — declared help groups and claimed help groups are equal in both directions.
- `buildConfigPatchFromFlags`'s discarded-flag warning — a flag with no config destination says so instead of succeeding silently.
- `explicit-runtime-exclusions.test.ts` — `RUNTIME_ONLY_FLAGS` stays disjoint from `FLAG_TO_CONFIG_PATH`, with `prompt`'s premise pinned separately.
- `RETIRED_MUSIC_MODEL_RATES` — retiring a priced model means moving its rate to a historical table, not deleting it.
- `links-registry-contracts.test.ts` plus the derived `fixtures/registry.ts` — links fixture expectations are read from the `model-links/*.json` registries at runtime instead of hand-maintained (see below).
- `llm-defaults.test.ts`'s "every `--llm` provider target has a config destination" — the selector table and `FLAG_TO_CONFIG_PATH` must agree, so a provider the help advertises cannot silently save nothing.
- `model-selector-messages.test.ts` — every `createModelValidator` key (collected at construction, so the list cannot be hand-maintained) resolves to a public selector, and every provider target round-trips to its own selector. A model validator whose provider is missing from the public selector tables fails here instead of shipping an error naming a flag nobody can type.
- `model-flags-and-ordering.test.ts`'s URL partition pin — `LOCAL_URL_ARTICLE_BACKENDS` and `HOSTED_URL_ARTICLE_BACKENDS` must partition `URL_ARTICLE_BACKENDS`, asserted through `isLocalUrlBackend` itself against the *hosted* list rather than the local one, so the check cannot restate the implementation. A registry entry whose `allShortcut` label drifts fails here instead of silently moving a backend between the local and hosted concurrency pools.
- `benchmark-contracts.test.ts`'s whisper-probe pin — the benchmark's local-service probe must call its injected `exists` with exactly `whisperBinaryPath`, imported from the module the whisper *runner* executes. A probe that goes back to a PATH lookup records no probed path and fails; a probe pointed at a different install location fails on the path comparison. Both arms of availability are asserted through the injected probe, so the guard does not depend on whether whisper is installed on the machine running the suite.
- `shipped-fixture-contracts.test.ts` — every path `git ls-files input/` reports must survive `git check-ignore --no-index`, so the index and the ignore rules cannot disagree. The expectation is read from the index rather than hand-listed, which is what keeps it from drifting the way the negation block itself did; `--no-index` is load-bearing, since plain `check-ignore` reports nothing for tracked paths and is precisely how the old breakage stayed invisible. Two further cases: the production constant `MISTRAL_DEFAULT_REF_AUDIO` must be shippable and present (a fixture the docs called committed while the rules dropped it), and five hypothetical personal-media paths must stay ignored, which pins the allowlist against being "simplified" into a glob. Because `--no-index` answers from the rules alone, that last case needs no file on disk and holds on any machine.
- `image-command-flag-spellings.test.ts` — `imageCommandOptionNames` and the flags the `image` command actually registers must agree in both directions, every internal spelling must retarget to exactly its public one (so a key that is a prefix of another key cannot silently rewrite it), and two real step-5 rejections are retargeted end to end. The rename map is the only home for the two spellings, so help text, argv normalization, and error text cannot drift apart.

**Formerly unguarded, now closed.** The `links` fixture constants in `test/test-cases/validation/content-output/metadata-links-lyrics-contracts/` were flagged here as the last unguarded drift mechanism, but that claim was stale on arrival: commit 2862a6e6 (2026-08-07) had already converted every fixture constant to runtime derivation — `provider-selector-groups/fixtures/registry.ts` reads the `model-links/*.json` registries from disk — and added `links-registry-contracts.test.ts` pinning registry integrity (unwired manifests, duplicate provider owners, cross-section URL dupes, absolute-URL form). The accepted residual: expectations and production read the same JSON, so a truncated or wrong-URL registry propagates silently; add a small hand-pinned sentinel (a few stable canonical URLs) only if registry truncation becomes a credible failure mode. A generator writing literal fixtures would be strictly worse — it reintroduces the on-disk copy that caused the drift in the first place.

## 3. Decided — one wave per decision

The ranked-options revision of this section is superseded (it survives in git history): the recommended option for every item is now the decision, and each decision below is a wave of its own. The wave counter restarts at 1 — Waves 1-17 in §1 are the earlier, closed mechanical series. These waves are independent: none depends on another, they can land one by one in any order, and each passes the §2 bar (`bun run check` plus the no-cost smoke set) before the next begins. No wave requires a paid-provider call to implement or verify. File:line references were verified 2026-08-07, and are stale for any file a landed wave has since touched.

All eighteen waves landed 2026-08-07 and are kept below as records rather than deleted, so the numbering stays stable and each decision keeps the account of how it differed from its prescription.

**Provider and model catalog**

**Wave 1 — Drop the `mistral-ocr-latest` alias. Landed 2026-08-07.** The no-moving-aliases policy in ADR-011/018/019 stood; the alias duplicated `mistral-ocr-4-0` byte-for-byte and made `--all-ocr` pay for the same model twice. `'mistral-ocr-latest'` is gone from `SUPPORTED_MISTRAL_OCR_MODELS` and its row is gone from `ocr-config/ocr-mistral.json`. Of the eight prescribed test sites, two retargeted to `mistral-ocr-4-0` verbatim (`mistral-rest-contracts.test.ts`, and `model-calibration.test.ts`, whose synthetic fixture description moved with the key); two were enumerations that simply lost a member (`provider-expansion-concurrency.test.ts:491`, and `ocr-pricing.test.ts`, whose two-target case became one target with `toHaveLength(1)` and `totalCost` 0.8); and four would have restated something the file already held verbatim, so they were deleted instead — `cli-usage-errors.test.ts:412` behind an existing `mistral-ocr-4-0` case, `provider-expansion-concurrency.test.ts:76` behind an existing acceptance, that file's `mistralLatestOcrOpts` pair whose `buildOptsFromFlags` call was identical to `mistralOcr4Opts`, and `price-commands/registry/ocr.ts:8` whose args matched the `mistral-ocr-4-0` command directly above it. To recover the coverage those deletions would have cost, `provider-expansion-concurrency.test.ts` gained a rejection pin on the full error string beside the existing `mistral-ocr-2405` one — a stronger guard than any of the retargets it replaced, since it fails if the alias is ever reintroduced. `03-extract-ocr.md` now states the alias is not accepted; ADR-011 carries the removal as a dated follow-up naming it the last selector contradicting that ADR's own "no `*-latest` alias" clause. Users who type the alias get the standard invalid-model error listing the concrete IDs, as intended.

**Wave 2 — Pin the `tts-1`/`tts-1-hd` re-check. Landed 2026-08-07.** Both rows kept; provider-side retirement is unverified and may not be verified by calling an API, so the open question was recorded exactly where the next refresh will read it. Both `pricingNotes` rows in `tts-config/tts-openai.json` now end with "Previous generation; verify provider retirement status at the next hosted-TTS model refresh.", and ADR-018 gained a Follow-up Actions row stating the question must be answered from OpenAI's published model documentation rather than by calling the API. `tts-models.ts` untouched; no code or test changes, as decided.

**Wave 3 — Delete Speechify's dead `voices` array. Landed 2026-08-07.** The TS constants stay the single home for the voice catalog, since they encode allow/deny behavior the flat registry list cannot: the deleted twelve-entry array was a flat merge of `SPEECHIFY_SIMBA_3_2_BUILT_IN_VOICES` and `SPEECHIFY_KNOWN_INCOMPATIBLE_BUILT_IN_VOICES`, which the merge erased the distinction between. The `voices` key is gone from `tts-config/tts-speechify.json`; the consumed `models` pricing block is untouched. No reader existed (`model-loader/tts.ts` exposes voice accessors only for kitten/groq/grok) and `voices` is optional in `TtsServiceSchema`, so validation and behavior are unchanged.

**Wave 4 — Remove the `costPer1kOutputChars` chain atomically. Landed 2026-08-07.** All nine sites went in one change, as prescribed: the two schema fields in `ExtractModelSchema`, the return-type field and converter read in `getExtractPricing`, the type fields on `ExtractStepEstimate` and `EstimatedStepEntry`, the `preflightToEstimated` copy, both `reporter.ts` arms, the `buildRatesUsed` spread in `ocr-costs.ts`, the `formatRatesSummary` `/1k chars` arm, and the two allowlist entries in `registry-provenance.test.ts`. Unproducibility was re-confirmed before the cut: no registry JSON carries either spelling, and no consumer spreads `getExtractPricing`'s result wholesale — every reader names the fields it copies, so the removed key could never reach an estimate. If a per-character-priced extract provider ever ships, rebuild mechanically from this list or git history.

**CLI surface**

**Wave 5 — Give llamafile a config destination (parity with `llama`). Landed 2026-08-07.** All five prescribed edits landed: `'llamafile'` added to `LLM_PROVIDER_FLAGS`, to the `d.llm` injectProviderGroup entries, and to `FLAG_TO_CONFIG_PATH` (→ `['defaults','llm','llamafile']`); `llamafile: ModelArraySchema` added to `LlmDefaultsSchema`; `'llamafile'` added to `REPEATABLE_MODEL_FLAGS` beside `'llama'`. Both halves were required together — the path entry alone would have made bare `config --llm llamafile` persist `true`, which `ModelArraySchema` then rejects on read; membership in `REPEATABLE_MODEL_FLAGS` routes it through `normalizeModelFlagOccurrences` instead. New `config-contracts/llm-defaults.test.ts` covers the single-model persist plus `loadConfig` round-trip, the repeated-selector array case, and a derived guard asserting every `WRITE_LLM_PROVIDER_TARGETS` value has a `FLAG_TO_CONFIG_PATH` entry. Residual asymmetry, deliberately out of scope: `llama` has a `DEFAULT_LOCAL_MODEL_BY_FLAG` entry so bare `--llm llama` resolves a default model, while `llamafile` has none, so bare `--llm llamafile` still selects nothing (unchanged from before this wave, in both the config and write paths).

**Wave 6 — Truthful model-validation errors. Landed 2026-08-07.** `createModelValidator` now formats through `describeModelSelector`, which splits the suffixes `-stt`/`-ocr`/`-tts`/`-image`/`-video`/`-music` into provider plus category and reads the public spelling back out of the seven target maps in `provider-targets.ts` (a leaf module with no imports, so the new dependency from `model-validation.ts` is cycle-free). The message shape moved from `Invalid --kimi-ocr model "X". Allowed values: …` to `Invalid model "X" for --provider/--ocr kimi[=model]. Allowed values: …`; the five `extraMessage` clauses that said "This flag" now say "This selector", since two flags are named. All 68 keys resolve with zero fallbacks (verified by enumeration), and the hand-written `validateLlamaModel` message in the same file was retargeted through the same formatter rather than left as the one surviving `--llama`. Pin updates: 23 literal `Invalid --<flag> model "<X>"` strings retargeted mechanically across five test files; the two loops keyed by internal flag (`model-flags-and-ordering.test.ts`, `tts-request-controls.test.ts`) now derive their expectation from `formatModelSelector`, keeping the flag-to-validator binding the old assertion had; four partial pins the `model` grep missed were fixed by hand, including `bfl-recraft-image-options.test.ts:41`, which pinned only `Invalid --recraft-image` and so was caught by the suite rather than the grep. Residual, deliberately out of scope: `setup --models whisperfile:bogus` names `--provider whisperfile[=model]` because the validator has no surface context — a real spelling that accepts that model, but not the one the user typed.

**Wave 7 — Bless the image command's prefix drop; remove the residue. Landed 2026-08-07.** The rename stood, as decided. `imageCommandOptionNames` is exported and `define-image-command.ts`'s byte-for-byte-duplicate `IMAGE_COMMAND_OPTION_FLAGS` is gone, so argv normalization and the flag definitions read the same map. The error-spelling half was larger than the finding stated: `--image-search-grounding` is hardcoded at nine sites, not two — the `IMAGE_OPTION_LABELS` entry plus seven per-provider `unsupported.push` calls and a Gemini list — and *every* `--image-*` label was wrong on this surface, not only that one, which three e2e files had pinned in nine assertions (`--image-aspect-ratio is not supported by BFL/flux-2-pro` for a user who typed `--aspect-ratio`). Retargeting each site individually would have left the prose clauses (`Supported Grok image options: --image-count, …`) still wrong, so the fix is one boundary retarget instead: `renameFlagSpellings` lifted out of `renameFlags` in `flag-utils.ts` (help text and error text now share one derived translation), applied to `AppUsageError` messages at the `image` command boundary. The handler body moved into `runImageCommand` so the wrapper is a five-line `try`/`catch` rather than an 88-line reindent. All nine e2e assertions were retargeted to the short spellings, `cli-usage-errors.test.ts` gained a two-case CLI-level pin, and `image-command-flag-spellings.test.ts` (§2) is the derived guard. The spelling note landed in all three standalone command docs (image, video, music), each citing ADR-012.

**Wave 8 — Hard error for `--tts-voice` in dialogue mode. Landed 2026-08-07.** The throw sits between `buildOptsFromFlags` and `collectTtsTargets` in the tts command handler, so it fires before preflight on both the single-file and directory paths, and the prescribed message shipped verbatim with a closing period, matching `target-validation.ts`. `TTS_GENERIC_OPTION_TARGETS['tts-voice']` is now exported as the derived `TTS_VOICE_OPTION_TARGETS`, so a twelfth provider voice target is covered without a second list. Dialogue presence reuses `isMultiSpeakerRequested` rather than re-reading the flags, which keeps the check and the mode switch in sync — including through Wave 9, which narrows that predicate to speaker mappings and adds its own error for the format-only case. Gating on `explicitFlags` was load-bearing exactly as predicted: `ttsSpeaker` always resolves (kitten's `'Jasper'` default), so a resolved-value check would have rejected every dialogue run. The provider-specific voice flags are unreachable here anyway — the `tts` command registers only the generic `--tts-voice`, which `normalizeGenericTtsOptionFlags` rewrites into a provider target before the check reads `explicitFlags`. No existing test or e2e run combined the two flags, so nothing needed migrating; `--tts-ref-audio` is the same class of conflict and stays out of scope, as decided. Docs: the two `text-to-speech.md` clauses that said `--tts-voice` is *ignored* under speaker mappings now say it is rejected, and note the config-default exemption.

**Wave 9 — Multi-speaker derives from mappings only. Landed 2026-08-07.** `isMultiSpeakerRequested` is now `(options.ttsSpeakers?.length ?? 0) > 0`, and `resolveDialogueFormat`'s rule that speaker mode requires a format is untouched, so the two halves of dialogue mode became one switch plus one requirement instead of two independent triggers. The warn/error pair ships as one exported `assertDialogueFormatIsUsable(options, explicitFlags?)` beside the predicate rather than as two inline checks, which is what let both entry points share it: the `tts` command handler passes `explicitFlags` and gets the hard error, while `runTts` — the pipeline's step-4 entry, and the only caller of the two, since the standalone command runs through `runTtsForTargets` — passes none and gets the warning, so no run can both warn and throw. That placement is the actual bug fix: the motivating case was a `ttsDialogueFormat` in config defaults aborting step 4 after three paid steps, and it now logs and continues single-speaker. Two throws went unreachable, not one: the named duplicate in `normalizeDialogueText` was deleted outright (an empty registry degrades to the existing no-turns error, and production cannot reach it anyway — `run-multi-speaker-tts.ts` runs only for targets that carry a `multiSpeakerStrategy`, which requires mappings), and `target-validation.ts:25-27` — which the finding had not counted — became unreachable for the same reason, so its `CLIUsageError` was replaced by an `InternalError` that narrows the optional `speakerVoiceRegistry` and no longer advertises a user-facing error that cannot fire. `input-validation.ts:11`'s `isMultiSpeakerRequested(options) && (options.ttsSpeakers?.length ?? 0) > 0` collapsed to its first clause, the two halves now being the same expression. Tests: the `tts-dialogue-contracts.test.ts` case that pinned the old format-only rejection was repointed to the surviving requirement (mappings without a format still throw `Dialogue TTS requires --tts-dialogue-format screenplay|labeled.`), and a new case pins the whole switch — format-only yields one target with no `multiSpeakerStrategy`, the same options warn without `explicitFlags` and throw with them, and adding mappings silences both arms — plus a CLI-level pin in `cli-usage-errors.test.ts`. Wave 8's `--tts-voice` error is deliberately unchanged: it reuses the narrowed predicate, so it now fires only when mappings are present, which is the only case in which a typed voice is actually discarded. Docs updated in `text-to-speech.md` (flag table and dialogue prose) and `config.md`; the `--tts-dialogue-format` help now says it requires `--tts-speaker`. Suite now 1262 pass across 185 files.

**Architecture**
